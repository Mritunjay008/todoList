# 🌟 Core Fundamentals: App Services, Secrets, Publish Profiles & Connection Strings

---

### **F1: What is an Azure Web App (App Service), and why do we use it?**

#### 💡 Simple Explanation:
Think of renting a computer:
- **IaaS (Virtual Machine):** You rent an empty computer. You have to install Windows/Linux, install security patches, install Node.js, install .NET, configure firewall ports, and reboot when Windows crashes.
- **PaaS (Azure Web App):** You rent an **already managed web hosting platform**. Microsoft manages the OS, security patches, auto-scaling, and SSL certificates. You only upload your application code (`dist/` or `.dll`).

#### ⚙️ Technical Breakdown:
- Azure App Service is a **Platform-as-a-Service (PaaS)** offering for hosting web applications, REST APIs, and mobile backends.
- It provides built-in auto-scaling, load balancing, health monitoring, automated HTTPS/TLS certificates, zero-downtime deployment slots, and VNet integration.

#### 🗣 What to Say to Your Lead:
> *"Azure Web App is a fully managed PaaS hosting platform. We use it because it eliminates the operational overhead of managing underlying virtual machine OS patches, web server configuration, and manual scaling, allowing us to focus purely on deploying application code."*

---

### **F2: What is an App Service Plan vs a Web App?**

#### 💡 Simple Explanation:
- **App Service Plan = The Physical Farm / Land (Compute & RAM):** It is the actual server CPU cores and Memory (e.g. 1 Core, 1.75 GB RAM) that you pay for in Azure.
- **Web App = The Houses built on that Land:** It is the individual website or API living on that server.
- You can host multiple Web Apps (e.g., both `todo-frontend` and `todo-backend`) on the **same App Service Plan** without paying double!

#### 🗣 What to Say to Your Lead:
> *"An App Service Plan represents the underlying compute infrastructure (CPU, RAM, and pricing tier), while a Web App is the hosted application running on that infrastructure. Multiple Web Apps can share a single App Service Plan to optimize cost."*

---

### **F3: What is a Publish Profile, what is inside it, and why do we use it?**

#### 💡 Simple Explanation:
A Publish Profile is a **digital VIP security key**. 
Instead of typing your personal Azure username and password into GitHub (which is insecure), Azure generates an encrypted XML file containing a dedicated, unique deployment username and a 64-character generated password specifically for deploying code to that one app.

#### ⚙️ Technical Breakdown:
When you open a `.PublishSettings` file, you see XML with two profiles:
1. **MSDeploy / OneDeploy profile:** Contains `publishUrl="https://<app>.scm.azurewebsites.net:443"`, `userName="$<app>"`, and `userPWD="<64-char-encrypted-secret>"`.
2. **FTP profile:** Contains FTP server credentials for uploading files.
- GitHub Actions uses the **MSDeploy / OneDeploy** credentials to push packages directly into `/home/site/wwwroot` over HTTPS without requiring interactive human login.

#### 🗣 What to Say to Your Lead:
> *"A Publish Profile is an XML configuration file generated by Azure containing the SCM deployment endpoint URL, MSDeploy authentication credentials, and user tokens. We use it in GitHub Actions to authenticate automated deployments without exposing personal Azure credentials."*

---

### **F4: Why do we integrate GitHub Secrets (`AZURE_FRONTEND_PUBLISH_PROFILE`, etc.)?**

#### 💡 Simple Explanation:
If you put your database password or publish profile password directly into your `ci-web.yml` file, anyone who can see your GitHub repository (or if the repo is made public) will see your passwords and can hack your Azure account!
**GitHub Secrets** is a **locked safe**. You put the password inside the safe, and GitHub encrypts it. Your workflow file only references the name of the secret, and GitHub automatically masks it in all logs with `***`.

#### ⚙️ Technical Breakdown:
- GitHub Secrets uses **libsodium public-key encryption** (Box encryption).
- Secrets are encrypted before they reach GitHub's servers and are only decrypted in memory inside the runner during job execution.
- GitHub automatically scrubs secret values from console output logs to prevent accidental credential leakage.

#### 🗣 What to Say to Your Lead:
> *"GitHub Secrets securely stores sensitive environment variables, API keys, and deployment credentials using encrypted vault storage. It prevents credential exposure in git history and automatically masks sensitive tokens in build logs."*

---

### **F5: What is a Connection String, and what does each part mean?**

#### 💡 Simple Explanation:
A Connection String is the **complete address and passport** that your backend API uses to find, unlock, and talk to your database.

#### ⚙️ Technical Breakdown (Dissecting the SQL Connection String):
```text
Server=tcp:todo-sql-server.database.windows.net,1433;Initial Catalog=tododb;User ID=sqladmin;Password=SecretPassword123!;Encrypt=True;TrustServerCertificate=False;Connection Timeout=30;
```
1. **`Server=tcp:todo-sql-server.database.windows.net,1433;`** ➔ The network location and TCP port (1433) of the database server.
2. **`Initial Catalog=tododb;`** ➔ The specific database name to open inside that server.
3. **`User ID=sqladmin; Password=...;`** ➔ The authentication credentials to prove who is logging in.
4. **`Encrypt=True;`** ➔ Forces all SQL query traffic over the network to be encrypted with TLS/SSL.
5. **`TrustServerCertificate=False;`** ➔ Validates that the server's SSL certificate is signed by a trusted certificate authority (prevents Man-In-The-Middle attacks).
6. **`Connection Timeout=30;`** ➔ Waits up to 30 seconds for the database to respond before timing out.

#### 🗣 What to Say to Your Lead:
> *"A Connection String is a structured string containing the host address, port, database catalog, credentials, and network encryption parameters required for an application to establish a secure ADO.NET session with a database."*

---

### **F6: What is the 'N' badge in the UI?**

#### 💡 Simple Explanation:
It is a **keyboard shortcut indicator** for power users.
When you press the letter **`N`** on your keyboard (without clicking anything), the app immediately opens the **"New Task"** creation modal dialog! Similarly, pressing **`/`** immediately focuses the Search bar.

# 🚀 1. GitHub Actions & CI/CD Pipelines

---

### **Q1: Why did we separate CI (Continuous Integration) and CD (Continuous Deployment) into two separate YAML files instead of one big file?**

#### 💡 Simple Explanation (Why this matters):
Imagine you are building a car. **CI is the factory quality check** (inspecting engine, testing brakes, crash testing). **CD is loading the verified car onto the delivery truck** and shipping it to the customer. 
If the engine fails quality checks in CI, you must never load it onto the delivery truck in CD. Separating them ensures that code is only deployed if it is 100% verified.

#### ⚙️ Technical Breakdown (Under the Hood):
- In [`ci-web.yml`](file:///C:/PersonalWorkspace/git-actions/todoList/.github/workflows/ci-web.yml) and [`ci-api.yml`](file:///C:/PersonalWorkspace/git-actions/todoList/.github/workflows/ci-api.yml), the CI pipeline runs automated unit tests, code linting (`oxlint` / `dotnet format`), and compiles the code into a release build artifact (`dist/` or `./publish`).
- In [`cd-web.yml`](file:///C:/PersonalWorkspace/git-actions/todoList/.github/workflows/cd-web.yml) and [`cd-api.yml`](file:///C:/PersonalWorkspace/git-actions/todoList/.github/workflows/cd-api.yml), the CD pipeline only executes when CI finishes with status `success`.
- **Benefit:** If you ever need to re-deploy a previously tested build to a different environment or rollback, you can re-run CD instantly without waiting 10 minutes for unit tests and linting to re-run.

#### 🗣 What to Say to Your Lead:
> *"We decoupled CI and CD to enforce strict quality gates. CI validates code quality through testing, linting, and building immutable release artifacts. CD listens for successful CI completions via `workflow_run` to deploy those artifacts, preventing broken code from ever touching our Azure environments."*

---

### **Q2: Why did we use `workflow_run` instead of `on: push` for the CD workflows?**

#### 💡 Simple Explanation:
If you put `on: push` in both `ci-web.yml` and `cd-web.yml`, when you push code to GitHub, **both workflows start running at the exact same second**. 
CD will immediately try to download the compiled build artifact from CI. But CI hasn't even finished compiling yet! CD will immediately crash with an error: *"Artifact not found"*.

#### ⚙️ Technical Breakdown:
- `on: workflow_run` creates a parent-child dependency between workflows:
  ```yaml
  on:
    workflow_run:
      workflows: ["Frontend CI Pipeline"]
      types: [completed]
  ```
- GitHub will only start the `cd-web.yml` runner **after** `Frontend CI Pipeline` has completed its run.
- In CD, we check `if: ${{ github.event.workflow_run.conclusion == 'success' }}` so that if tests fail in CI, CD is completely skipped.

#### 🗣 What to Say to Your Lead:
> *"If CD triggered on `push`, it would run concurrently with CI and fail because the build artifact hasn't been created yet. `workflow_run` guarantees sequential execution: CD only wakes up after CI finishes and passes all tests."*

---

### **Q3: What are GitHub Actions Artifacts (`upload-artifact` and `download-artifact`), and where are they stored?**

#### 💡 Simple Explanation:
Think of an artifact as a **sealed package**. 
CI builds the application (compiling React into `dist/` or .NET into `.dll` binaries), puts those files into a sealed `.zip` package, and uploads it to GitHub. CD downloads that exact sealed package and unpacks it directly into Azure.

#### ⚙️ Technical Breakdown:
- `actions/upload-artifact@v4` uploads files to **GitHub Actions Cloud Storage** attached to that specific workflow run ID.
- `actions/download-artifact@v4` pulls that package into the CD runner's filesystem.
- **Why this is a DevOps Best Practice:** You compile your code **only once**. What you test in CI is 100% identical byte-for-byte to what you deploy in CD. You avoid "it worked on the build machine but failed on deployment" bugs.

#### 🗣 What to Say to Your Lead:
> *"We use GitHub Artifacts to implement the 'Build Once, Deploy Anywhere' principle. CI packages our compiled binaries into GitHub's cloud artifact storage, and CD downloads that verified immutable package to push directly to Azure App Service."*

---

### **Q4: Why did we configure `retention-days: 7` on artifacts?**

#### 💡 Simple Explanation:
GitHub provides a limited storage quota for artifacts (e.g., 500MB on free accounts, or billed per GB on enterprise). If you keep every build artifact forever, you will run out of storage or receive unexpected cloud bills.

#### ⚙️ Technical Breakdown:
- `retention-days: 7` instructs GitHub Actions to automatically delete the uploaded zip files 7 days after the workflow run finishes.
- 7 days is the industry standard sweet spot: it gives you a full week to download or inspect build logs if an issue occurs, while keeping repository storage costs at zero.

---

### **Q5: Why is `workflow_dispatch` added to all our workflow YAML files?**

#### 💡 Simple Explanation:
Normally, workflows only run when someone pushes code (`git push`). But what if you want to test the deployment right now without making a dummy code commit? `workflow_dispatch` gives you a **manual "Run workflow" button** in the GitHub web interface.

#### ⚙️ Technical Breakdown:
- Adding `workflow_dispatch:` under the `on:` trigger enables the interactive "Run workflow" dropdown button in GitHub Actions tab.
- This is essential for operations teams and emergency manual hotfix rollbacks.

---

### **Q6: Why did we use `paths:` filters in `ci-web.yml` and `ci-api.yml`?**

#### 💡 Simple Explanation:
Our repository is a **monorepo** containing both the React `frontend/` and the .NET `backend/`. 
If a developer only changes a CSS color in the frontend, it makes no sense to waste 5 minutes compiling C# backend code and running database tests!

#### ⚙️ Technical Breakdown:
```yaml
paths:
  - 'frontend/**'
  - '.github/workflows/ci-web.yml'
```
- GitHub checks the git commit diff. If none of the changed files match the `paths:` pattern, GitHub skips the workflow entirely.
- **Result:** Saves CI/CD compute minutes, keeps pull request checks fast, and prevents unnecessary cloud deployments.

---

### **Q7: What does `defaults: run: working-directory: frontend` do?**

#### 💡 Simple Explanation:
By default, GitHub Actions runs all terminal commands at the very root of your git repository. But `package.json` is located inside the `frontend` subfolder. Without this setting, running `npm install` would fail because npm cannot find `package.json` at the root.

#### ⚙️ Technical Breakdown:
- `defaults: run: working-directory: frontend` tells the GitHub Actions runner: *"For every `run:` step in this job, automatically `cd frontend` before executing the command."*

---

### **Q8: How does `cache: 'npm'` in `actions/setup-node` speed up CI?**

#### 💡 Simple Explanation:
Every time a GitHub Actions runner starts, it is a brand-new virtual machine with an empty hard drive. Running `npm install` from scratch takes 45–60 seconds downloading 200+ packages over the internet. Caching saves those downloaded packages so subsequent builds finish `npm install` in 3 seconds.

#### ⚙️ Technical Breakdown:
- `cache-dependency-path: frontend/package-lock.json` computes an MD5/SHA256 hash of your lockfile.
- If `package-lock.json` has not changed since the last run, `setup-node` restores the cached `~/.npm` directory from GitHub's cache storage instead of reaching out to the public npm registry.

---

### **Q9: How does `azure/webapps-deploy@v3` work under the hood?**

#### 💡 Simple Explanation:
It acts as the automated delivery driver. It takes your compiled zip file (`frontend/dist` or `./publish`), connects to Azure App Service's background management server (called Kudu / SCM), authenticates using your Publish Profile key, and unpacks the files into Azure's web directory (`/home/site/wwwroot`).

#### ⚙️ Technical Breakdown:
- It makes an HTTPS POST request to `https://<app-name>.scm.azurewebsites.net/api/publish?type=zip`.
- It uses HTTP Basic Authentication using the deployment username and password extracted from the `.PublishSettings` XML file stored in GitHub Secrets.

---

### **Q10: Why did the deployment fail when `AZURE_FRONTEND_APP_NAME` had `.azurewebsites.net` in it?**

#### 💡 Simple Explanation:
Azure App Service resources are named by their **short identifier** (e.g. `todo-frontend-fzh4bzavcegngqc9`), not their full URL. The GitHub Action expects just the resource name. If you paste the full URL, the action looks for an app called `todo-frontend...azurewebsites.net.azurewebsites.net`, which doesn't exist.

# 🌐 2. Azure Virtual Network (VNet) & Subnetting

---

### **Q11: What is an Azure Virtual Network (VNet) and why did we assign `10.0.0.0/16`?**

#### 💡 Simple Explanation:
A Virtual Network (VNet) is your own **private, isolated datacenter network in the cloud**. No one on the public internet can enter this network unless you explicitly create a public door.
`10.0.0.0/16` is the size of the whole neighborhood (65,536 private IP addresses), which you can slice into smaller streets (subnets).

#### ⚙️ Technical Breakdown:
- `10.0.0.0/16` is an RFC 1918 private IPv4 CIDR block spanning `10.0.0.0` to `10.0.255.255`.
- We assign a large `/16` address space at the root so that in the future, if you need to add Redis Cache, Kubernetes clusters, or Container Apps, you have thousands of available IP ranges without having to recreate the VNet.

---

### **Q12: Why are our subnets sized as `/24`? How many usable IPs are in a `/24`?**

#### 💡 Simple Explanation:
A `/24` subnet contains **256 total IP addresses**. However, in Azure, you can only use **251 IP addresses** because Azure takes 5 IPs for its own management.

#### ⚙️ Technical Breakdown (The 5 Reserved IPs in every Azure Subnet):
If your subnet is `10.0.1.0/24`:
1. `10.0.1.0`: **Network Address** (identifies the subnet).
2. `10.0.1.1`: **Default Gateway** (routes traffic out of the subnet).
3. `10.0.1.2` & `10.0.1.3`: **Azure DNS Mapping** (resolves Azure internal DNS).
4. `10.0.1.255`: **Broadcast Address** (network broadcast).
- **Why `/24` is ideal:** Azure App Service VNet integration requires a minimum `/28` (16 IPs). A `/24` (251 usable IPs) allows the App Service to horizontally autoscale to dozens of instances during high traffic spikes without running out of private IP addresses.

---

### **Q13: What is Subnet Delegation (`Microsoft.Web/serverFarms`), and why is it mandatory for App Service?**

#### 💡 Simple Explanation:
By default, Azure subnets are generic—they expect Virtual Machines or network cards. 
When you set Subnet Delegation to `Microsoft.Web/serverFarms`, you are putting up a sign that says: *"This subnet is reserved exclusively for Azure App Service to use for sending outbound traffic."*

#### ⚙️ Technical Breakdown:
- When an App Service connects to a VNet (Outbound VNet Integration), Azure must inject dedicated network routing software and internal load balancers into that subnet.
- Setting delegation to `Microsoft.Web/serverFarms` grants the App Service resource provider the permissions required to manage those internal networking adapters.

---

### **Q14: Why can't we use the exact same subnet for both Inbound Private Endpoint and Outbound VNet Integration?**

#### 💡 Simple Explanation:
Think of an **Inbound Private Endpoint as an Entrance Door** (traffic coming IN). Think of **Outbound VNet Integration as a Highway Exit Ramp** (traffic going OUT).
Azure networking rules prohibit mixing an Entrance Door and a Highway Exit Ramp in the same subnet for the same App Service.

#### ⚙️ Technical Breakdown:
- **Inbound Private Endpoint:** Requires a standard, non-delegated subnet because it assigns a static private Network Interface Card (NIC) with a private IP (`10.0.2.x`).
- **Outbound VNet Integration:** Strictly requires a subnet delegated to `Microsoft.Web/serverFarms`.
- Because a subnet cannot be simultaneously delegated to `serverFarms` and contain standard Private Endpoints for the same App Service instance, they must be separated into different subnets (`backend-subnet` for inbound, `frontend-subnet` or `backend-egress-subnet` for outbound).

---

### **Q15: Why did `todo-frontend` and `todo-backend` end up sharing `frontend-subnet` for outbound traffic?**

#### 💡 Simple Explanation:
Both `todo-frontend` and `todo-backend` were created inside the **same App Service Plan** (the underlying compute server). 
In Azure, the App Service Plan is the actual physical host. All web applications living on the same host must share that host's outbound network connection (`frontend-subnet`).

#### ⚙️ Technical Breakdown:
- An App Service Plan defines the VM instance scale. VNet integration operates at the App Service Plan worker level.
- When `todo-frontend` joined `frontend-subnet`, the underlying App Service Plan became bound to that subnet. When `todo-backend` joined the VNet, Azure attached it to the same outbound subnet because they share the plan.

---

### **Q16: Why did we disable Azure Bastion and DDoS Network Protection during VNet creation?**

#### 💡 Simple Explanation:
- **Azure Bastion:** It is a remote desktop tool used to log into Virtual Machines (like Windows Server / Ubuntu VMs). We are using PaaS Web Apps and PaaS SQL (serverless/managed), so we have zero VMs. Enabling Bastion would do nothing and cost **$140/month**.
- **DDoS Network Protection Plan:** Costs **$3,000/month** and is meant for banks with massive public IP ranges. Azure already provides free basic DDoS protection for all App Services.

# 🔒 3. Private Endpoints & Azure Private Link

---

### **Q17: What is an Azure Private Endpoint and how does it work?**

#### 💡 Simple Explanation:
Normally, Azure Web Apps and Azure SQL have public internet URLs. 
A **Private Endpoint** cuts off the public internet wire and attaches a **private network card (NIC) with an internal IP (like `10.0.2.4`)** inside your private VNet. The service can now only be reached by computers inside that VNet.

#### ⚙️ Technical Breakdown:
- A Private Endpoint creates a Virtual Network Interface (NIC) inside the chosen subnet.
- Traffic travels privately across the Microsoft Azure Global Backbone network without ever traversing the public internet.
- All public DNS queries outside the VNet are returned as blocked or unresolvable.

---

### **Q18: What is a Private DNS Zone (`privatelink.azurewebsites.net` and `privatelink.database.windows.net`), and why is it mandatory?**

#### 💡 Simple Explanation:
If your backend's private IP is `10.0.2.4`, your frontend code doesn't want to hardcode `http://10.0.2.4` (because private IPs can change, and HTTPS SSL certificates are issued for domain names, not IPs!).
The **Private DNS Zone** is an internal phonebook inside Azure. When the frontend asks: *"What is the IP of `todo-api.azurewebsites.net`?"*, the Private DNS Zone answers: *"Inside this VNet, it is `10.0.2.4`!"*

#### ⚙️ Technical Breakdown:
- When a Private Endpoint is created with Private DNS integration enabled, Azure creates an `A Record` inside `privatelink.azurewebsites.net` mapping `todo-api` to `10.0.2.4`.
- A CNAME record maps `todo-api.azurewebsites.net` ➔ `todo-api.privatelink.azurewebsites.net`.
- When an app inside the VNet queries `todo-api.azurewebsites.net`, the VNet DNS automatically resolves it to the private IP `10.0.2.4`.

---

### **Q19: What is `WEBSITE_VNET_ROUTE_ALL=1` and why was it required?**

#### 💡 Simple Explanation:
By default, an App Service connected to a VNet only sends traffic through the VNet if the target address is explicitly a private IP (like `10.x.x.x`). 
If the app makes a request to a domain name (like `https://todo-api.azurewebsites.net`), Azure thinks: *"That's a public domain name, I will send it over the public internet!"*—which immediately fails because the backend is private!
`WEBSITE_VNET_ROUTE_ALL=1` forces **100% of all outgoing requests** to travel through the VNet.

---

### **Q20: What is `WEBSITE_DNS_SERVER=168.63.129.16` and why was it required?**

#### 💡 Simple Explanation:
**`168.63.129.16`** is the special magic IP address of Azure's internal DNS server. 
Setting `WEBSITE_DNS_SERVER=168.63.129.16` forces the Frontend App Service to ask Azure's internal private DNS server for domain names, allowing it to find the private IP of the Backend and Azure SQL Database.

# 🚪 4. App Service Security & Access Restrictions

---

### **Q21: What is SCM (Kudu) and why does every Web App have two URLs?**

#### 💡 Simple Explanation:
Every Azure Web App actually has **two sites**:
1. **Main Site (`https://todo-api.azurewebsites.net`):** The customer-facing API that serves user HTTP requests.
2. **SCM Site (`https://todo-api.scm.azurewebsites.net`):** The administrative management engine (Kudu) used for deploying code, viewing live logs, and uploading zip packages.

---

### **Q22: What caused the `403 Ip Forbidden` deployment error on the Backend Web App?**

#### 💡 Simple Explanation:
When we set the Backend Web App to "Private Endpoint Only / Disable Public Access", Azure's firewall locked **both** the Main API site AND the SCM deployment site.
When GitHub Actions tried to upload the backend `.dll` files from GitHub's cloud servers, Azure's firewall blocked GitHub with a `403 Forbidden` error.

---

### **Q23: How did we resolve `403 Ip Forbidden` while still keeping the API 100% private?**

#### 💡 Simple Explanation:
We used Azure's **Access Restrictions Uncoupling** feature:
- We told Azure: *"Keep the **Main API site** locked to `Deny` (private to VNet only)."*
- *"Uncouple the **SCM deployment site** and set it to `Allow` so GitHub Actions can deploy using the Publish Profile password."*

#### ⚙️ Technical Breakdown:
- In Azure Portal ➔ Backend App ➔ **Networking ➔ Public network access**:
  - Main Site: Default action = **`Deny`**.
  - Advanced Tool (SCM) site: Default action = **`Allow`**.
- **Security Validation:** Even though SCM is accessible over the internet, it is protected by TLS encryption and strong 64-character deployment credentials in the Publish Profile XML. The actual REST API endpoints (`/api/todos`) remain strictly private inside the VNet.

---

### **Q24: What is SCM Basic Authentication and why did we have to turn it ON?**

#### 💡 Simple Explanation:
Basic Authentication means logging in with a **Username and Password** (which is what GitHub Actions Publish Profiles use).
Microsoft disables username/password login by default on brand-new Azure tenants to encourage users to use complex Managed Identity tokens. We turned it **ON** so GitHub Actions could use the downloaded Publish Profile credentials.

# 🗄 5. Azure SQL Database (PaaS) & Data Security

---

### **Q25: What port does Azure SQL listen on?**

#### 💡 Simple Explanation:
**Port 1433** over TCP.

---

### **Q26: Why did we choose SQL Authentication instead of Microsoft Entra Only Authentication?**

#### 💡 Simple Explanation:
SQL Authentication lets you set an admin username (e.g. `sqladmin`) and password. This allows you to construct a standard ADO.NET connection string.
If you choose Microsoft Entra Only, password connection strings are disabled, requiring you to configure Azure Managed Identities, Azure AD app registrations, and database role grants, which adds unnecessary complexity for this setup.

---

### **Q27: Why did we choose Basic Tier (5 DTU, ~$5/mo) instead of the default General Purpose tier?**

#### 💡 Simple Explanation:
When you click "Create SQL Database", Azure defaults to **General Purpose Provisioned (2 vCores)**, which costs **$150 to $250 every month**.
For a development/test application, switching to **Basic tier (5 DTU, 2GB storage)** costs only **~$5/month**, saving 98% of database costs while providing the exact same SQL Server features and Private Endpoint support.

---

### **Q28: Is the Azure SQL Database accessible from the public internet?**

#### 💡 Simple Explanation:
**No.** Public Network Access is completely set to **Disabled**. All public firewall rules are closed.
The only way to reach the SQL Database is through its **Private Endpoint (`10.0.3.x`)** inside `database-subnet` over port `1433`.

---

### **Q29: What does `EnableRetryOnFailure` in EF Core do?**

#### 💡 Simple Explanation:
In cloud environments, network connections can occasionally drop for a fraction of a millisecond during database failovers or router refreshes.
`EnableRetryOnFailure(5)` instructs the Entity Framework Core client to retry failed connection attempts up to 5 times before throwing an exception.

# 🔄 6. Reverse Proxy, SPA Hosting & Troubleshooting

---

### **Q30: What is the BFF (Backend-For-Frontend) Reverse Proxy pattern and why do we use it?**

#### 💡 Simple Explanation:
Because the Backend Web App is completely private (no public IP), a user's browser in Chrome at home cannot connect to `todo-api.azurewebsites.net`.
Instead, the user's browser talks to the **Public Frontend (`todo-frontend.azurewebsites.net/api/todos`)**. 
The Frontend server ([`server.js`](file:///C:/PersonalWorkspace/git-actions/todoList/frontend/public/server.js)) catches that request and forwards it privately over the Azure VNet to the Backend API.

```
[ User Browser (Home) ] ➔ Public HTTPS ➔ [ Frontend Web App ] ➔ Private VNet ➔ [ Backend Web App ] ➔ Private VNet ➔ [ Azure SQL ]
```

---

### **Q31: Why did the Frontend show a blank page on Azure Linux initially?**

#### 💡 Simple Explanation:
React/Vite compiles into static files (`index.html`, `index.js`, `index.css`).

### **Q32: What caused the `502 Bad Gateway` error and how did we diagnose and resolve it?**

#### 💡 Simple Explanation:
A `502 Bad Gateway` is a networking error meaning: *"The Frontend proxy received the request, but when it tried to reach the Backend server, it could not connect."*

#### ⚙️ Technical Diagnosis & Fix:
1. **Diagnosis:** The Frontend was attempting to look up `todo-api.azurewebsites.net` on public DNS. Because public access was disabled on the backend, public DNS returned nothing, and the TCP connection timed out.
2. **Fix:** We added two settings to the Frontend Web App:
   - `WEBSITE_VNET_ROUTE_ALL = 1`: Forces the request through the VNet.
   - `WEBSITE_DNS_SERVER = 168.63.129.16`: Uses Azure's internal Private DNS resolver to resolve `todo-api` to its private IP `10.0.2.x`.
   - Result: TCP connection succeeded over VNet and the `502` error disappeared.
